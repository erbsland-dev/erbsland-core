# Compression algorithm profiler

`compression-profile` measures one-shot `ByteCompressor::compress` and `ByteDecompressor::decompress` calls through
the common profiling framework. Fixture loading, deterministic corpus generation, decoder-input preparation,
maximum-length checks, and exact round-trip validation happen before measured work. Each worker owns its configured
codec wrapper and shares immutable source and encoded bytes.
The timed worker loop performs only in-memory compression or decompression. It does not open, read, write, or close
files, and result comparison runs after each timed sample.

The profiler reports uncompressed and compressed byte counters and rates. The uncompressed rate is the logical
throughput normally used to compare algorithms; dividing compressed bytes by uncompressed bytes gives the compression
ratio. Each prepared scenario also emits a `record=compression-size` line with `input-bytes`, `compressed-bytes`,
`size-ratio` (compressed/input), `savings-percent`, and `reduced`. A ratio below 1 means smaller output; 1 or above
means no reduction. These are exact fixture sizes including the selected format's framing, independent of timed
operation counts. Entropy and tiny inputs can legitimately expand, and Deflate/Fastest deliberately uses stored
blocks. Inspect ratios as well as throughput: a codec that falls back to storing everything can appear faster.
Compression levels on decompression scenarios identify the level used to prepare the encoded fixture.

## Corpus

The checked-in seeds provide multilingual prose, structured JSON records, and C++-like source. The generator expands
these seeds to the requested size with deterministic separators and also creates the following binary workloads:

- `runs` combines short and extended runs around common token and RLE boundaries.
- `matches` combines near, 32 KiB, 64 KiB, and longer-distance matches with controlled mutations.
- `sparse-binary` contains mostly zero-valued records with counters and random islands.
- `entropy` contains uniformly distributed deterministic bytes for incompressible/stored paths.
- `mixed` combines runs, matches, sparse records, and entropy in one input.

Generated bytes depend only on the run seed, corpus ID, and input size. Equivalent scenarios therefore receive
identical source bytes regardless of operation, algorithm, format, or level. The catalog records a stable FNV-1a
digest for every corpus at the default seed and 1 MiB size; those canonical inputs are checked when prepared.
Generated random bytes use the low byte of each `std::mt19937_64` output so their digests are identical across C++
standard-library implementations.
Because entropy inputs commonly select stored or literal-only representations, their decompression rates primarily
measure the codec's validated memory-copy path. Use `matches` or `mixed` when comparing match-decoding performance.

## Suites and commands

The default `snapshot` suite runs both operations for every algorithm and corpus using raw/default compression. The
`levels` suite covers every compression level over `mixed`, `formats` covers every supported representation over
`structured`, and `full` expands the complete compatible cross-product. LZ4/ZIP is rejected because the library does
not support that representation. The inexpensive `smoke` suite exercises every algorithm and loads every corpus.

The `windows` suite adds 120 Raw scenarios: both operations, four native codecs, all five levels, and `matches`,
`entropy`, and `mixed`. Inputs cover at least four configured dictionaries/windows, with an 8 MiB floor. LZMA sizes
are 8/8/32/64/128 MiB and Zstandard sizes are 8/8/8/32/128 MiB from Fastest to Highest; Deflate and Bzip2 use 8 MiB.
This exposes history compaction and index rebasing costs hidden by the 1 MiB snapshot. It measures complete memory
operations, not peak streaming workspace: source, encoded fixtures, and retained sample results also use memory.
Use a larger memory budget and fewer samples, for example:

```shell
cmake-build-profile/profiling-apps/compression-profile --suite windows --level default --samples 1 --warmup-samples 0 --minimum-sample-time 100us --memory-limit '1 GiB' --duration 10m
```

Use `--algorithm` and `--corpus` to narrow this expensive suite. The normal memory checks still apply, so large
scenarios can require higher budgets if more worker results or samples are retained.

Build and inspect an optimized snapshot with:

```shell
cmake -S . -B cmake-build-profile -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo
cmake --build cmake-build-profile --target compression-profile -j 8
cmake-build-profile/profiling-apps/compression-profile --dry-run
cmake-build-profile/profiling-apps/compression-profile --algorithm deflate --corpus structured
```

Use `--suite levels`, `--suite formats`, or repeat axis filters for focused comparisons. The `full` suite contains
1,120 scenarios at the default size, so select a subset or explicitly increase `--duration` and reduce `--samples`
when running it. Custom ELCL scenarios accept `Algorithm`, `Format`, `Level`, `Corpus`, and `Input Size` fields.
`--list-scenarios`, `--list-coverage`, `--mode`, `--threads`, and the other common framework options are also
available.

Use the same executable, configuration digest, seed, thread count, build type, and machine conditions for comparisons.
Prefer medians from several complete benchmark runs and inspect p95, maximum latency, and worker fairness separately.
